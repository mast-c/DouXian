# medical_* 文件用途与清理建议

检查日期：2026-10-30。范围：data/ 下的 medical_* 文件，以及主程序、测试、操作说明中的引用。本次为静态代码与报告审查，没有执行应用、联网、连接数据库或删除文件。未发现引用不等于从未手工运行。

## 结论

当前有 15 个 medical_*.py，合计约 199.7 KiB。不能统一认定为无用旧文件。6 个是当前问答或页面的直接依赖，3 个支持数据入库扩容，4 个用于验收评测，2 个是可选的单药试点或单问题诊断工具。没有发现可以无条件断定为无用的 Python 文件。

如果目标只是清爽目录，优先归档历史报告；若不再需要早期单药试点与单问题诊断，再考虑归档 medical_json_index.py、medical_hybrid_probe.py。两者合计 16,067 字节（约 15.7 KiB），删除并不能明显节省磁盘。不要仅因文件标注旧版本号就删除。

## 2. 入库与扩容：保留

| 文件 | 实际用途 | 依赖/替代关系 | 建议 |
| --- | --- | --- | --- |
| medical_json_chunker.py | 对清洗药品 JSON 按栏目及原文结构切分，匹配 Neo4j 原文位置，生成 Chroma 文档和稳定 ID | medical_json_index.py、medical_json_bulk_index.py 均导入；有独立测试 | 保留，是公共入库基础模块 |
| medical_json_bulk_index.py | 批量增量导入；支持指定药名、来源核验、预算、已有片段复用和 SQLite 断点记录 | medical_expand_batch.py 动态导入 main；读取/写入 medical_bulk_state.sqlite3 | 保留，是当前扩容执行器 |

这些脚本不一定在每次聊天时运行，但仍是知识库维护流程的一部分。删除不会抹掉已存在的 Chroma 文档，却会丢失后续扩容能力。

## 3. 验收与评测：有用途，建议保留

| 文件 | 实际用途 | 与其他文件的区别 | 建议 |
| --- | --- | --- | --- |
| medical_chroma_acceptance.py | 检查当前 Chroma 文档的元数据、正文 SHA-256、重复 ID 等；可抽样回查 Neo4j 原文 | 面向数据库中的索引数据质量；不是回答质量检查 | 扩容后仍有用，保留 |
| medical_eval_workbench.py | audit 审计知识库覆盖；draft 生成待人工审核题库；score 按人工 Gold Section ID 计算检索指标；compare 对照报告 | 相比 retrieval_eval 使用更严格的人工 Section 级金标准；quality_campaign 的双检索报告对比还会调用它 | 保留；V1.16/V1.17 指南仍引用 |
| medical_quality_campaign.py | 批量读取页面导出的 trace，生成工程检查汇总、人工审核表及人工质量统计 | 调用 quality_acceptance；面向一批回答，不能由单轮检查完全替代 | 保留，属于 V1.17 质量基线流程 |
| medical_retrieval_eval.py | 对 JSONL 测试题统计目标药品/栏目命中及跨药品污染，比较实体约束前后结果 | 不等于人工 Gold Section 的 Recall@K；workbench 有重叠但指标和输入格式不同 | 建议保留；若明确不再使用旧轻量基线，可归档，不能宣称完全重复 |

medical_chroma_acceptance.py 读取 Chroma，可选只读访问 Neo4j；medical_eval_workbench.py 的检索评分可选云端查询。medical_quality_acceptance.py 与 medical_quality_campaign.py 的离线检查不连接数据库或云服务。本次未运行这些命令。

## 4. 可选归档候选：不是完全无用

| 文件 | 实际用途 | 可归档条件 | 关联影响 |
| --- | --- | --- | --- |
| medical_json_index.py | 早期单药品 JSON → Neo4j 核验 → Chroma 试点工具，可预览并限制片段数量 | 已统一使用 medical_json_bulk_index.py（也支持 --drug），且不再需要此独立试点入口 | tests/test_medical_json.py 会读取此文件做预览/写入安全断言；直接删除会使相关测试失败。medical_hybrid_probe.py 的空库提示也仍提到它 |

两者均未被当前 rag.py、豆馅.py 直接导入。归档前应一起调整测试或测试加载位置及提示语；本次没有改测试或业务逻辑。

## 6. 最小清理建议

1. 当前在线问答所需的 6 个模块全部保留，尤其不要误删 medical_quality_acceptance.py。
2. 保留入库公共切分器、批量执行器、批次调度器和 SQLite 断点。
3. 确实不再做早期试点/单问题诊断时，归档 medical_json_index.py、medical_hybrid_probe.py，同时处理测试引用。
4. 不需要旧入库/审计记录时，3 个 JSON 可以删除；若需要追溯，归档比删除更合适。
5. 当前没有发现任何可不附加条件就认定为废弃的 medical_*.py。若目的仅是节省空间，删除这些小脚本收益很小。
